# 构建踩坑记录

围绕「改名 + 换图标 + 换背景 + 内置整合包」这几轮改动，实际踩到的坑与结论。
每条都是**实测验证过的**，不是推测。

---

## 1. Gradle 读 .properties 用 ISO-8859-1，中文会乱码

**现象**：桌面图标名显示为乱码方块。

**根因**：`java.util.Properties.load()` 规定按 **ISO-8859-1** 解码。
中文直接写在 `gradle.properties` 里，Gradle 读进来已是一堆拉丁字符，
再经 UTF-8 输出 → **双重编码**。

实测字节对比（目标字符「山之城」，UTF-8 应为 9 字节）：

| 写法 | 实际字节数 | 结果 |
|---|---|---|
| 直接写中文 | 18 | 乱码（`303 245 302 261 ...`） |
| `\u5c71\u4e4b\u57ce` | 9 | 正常（`345 261 261 344 271 213 345 237 216`） |

**结论**：`launcher_app_name` / `launcher_short_name` 一律用 `\uXXXX` 转义。
`launcher_name`（APK 文件名）用 ASCII，避免下游工具再出编码问题。

## 2. `unzip -l` 看不到签名文件 ≠ 未签名

**现象**：`unzip -l app.apk | grep '\.RSA'` 无输出，误判为「没签名」。

**根因**：项目用的 **AGP 9.3.0，默认只启用 v2 签名**（minSdk 26 完全够用）。
v2/v3 签名写在 **APK Signing Block**——位于 ZIP 中央目录之后的一段独立数据，
**不产生 `META-INF/*.RSA` / `*.SF`**。只有 v1（JAR signing）才会。

**正确验证方式**：

```bash
java -jar $ANDROID_SDK/build-tools/34.0.0/lib/apksigner.jar \
  verify --print-certs -v app.apk
```

期望输出：

```
Verifies
Verified using v2 scheme (APK Signature Scheme v2): true
Signer #1 certificate SHA-256 digest: 8adad0d5...342d091d
```

**顺带一提**：`build-tools/36.0.0/apksigner` 直接执行会报
`Unsupported command`，改用 `34.0.0`，或直接 `java -jar .../apksigner.jar`。

## 3. `packageDebug` UP-TO-DATE 可能导致产物没签名

**现象**：`packageDebug` 显示执行过，但产物验证报
`INSTALL_PARSE_FAILED_NO_CERTIFICATES`。

**根因组合**：`build/intermediates/apk/debug` 与
`build/intermediates/signing_config_versions` 的缓存状态与实际产物不一致
（在 `--offline` + 反复中断的构建里容易出现）。

**处理**：

```bash
rm -rf ZalithLauncher/build/outputs/apk/debug \
       ZalithLauncher/build/intermediates/apk/debug \
       ZalithLauncher/build/intermediates/signing_config_versions
./gradlew :ZalithLauncher:packageDebug --no-daemon --offline
```

**自检**：`./gradlew :ZalithLauncher:signingReport` 应能列出
debug variant 的 Store / Alias / SHA-256。列不出说明配置没生效。

## 4. GitHub Release 的 asset 名不接受非 ASCII

**现象**：上传 `山之城-Debug-2.5.3.apk`，接口返回 422
`ReleaseAsset.name already exists`；换个时机上传，文件名被静默改成
`-Debug-2.5.3.apk`（中文前缀被剥掉）。

**结论**：asset 名一律用 ASCII。`launcher_name=ShanZhiCheng` 正是为此。

## 5. 上传大文件到 Release 的正确姿势

```bash
# ❌ 1.3 GB 用 --data-binary 会读进内存
curl: option --data-binary: out of memory

# ❌ 显式 chunked 会被拒
{"message":"Bad Content-Length"}

# ✅ 带 Content-Length 的流式上传（实测可用）
SIZE=$(stat -c%s app.apk)
curl -X POST \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Content-Type: application/vnd.android.package-archive" \
  -H "Content-Length: $SIZE" \
  -T app.apk \
  "https://uploads.github.com/repos/<owner>/<repo>/releases/<id>/assets?name=app.apk"
```

`gh release upload --clobber` 也能用，但它会**先删同名 asset 再建**；
若该 asset 已被手工删除，会报 404 而非自动走创建流程。

## 6. 容器构建环境（非本机，可忽略）

| 项 | 值 | 影响 |
|---|---|---|
| cgroup 内存上限 | 8 GB（`cat /sys/fs/cgroup/memory.max`） | 堆给大 → dex 阶段被 OOM Kill，报 `daemon disappeared unexpectedly` |
| 网络 | google()/mavenCentral() 可达但零数据 | 必须 `--offline`，否则卡几十分钟 |
| 文件系统 | overlayfs | **不在 Gradle VFS 支持列表**，偶发 `Failed to create MD5 hash for file`，重试即过 |

**可用构建命令**：

```bash
./gradlew :ZalithLauncher:assembleDebug --no-daemon --offline
```

增量正常时约 **30～50 秒**（关键：900 MB 的 xz 资源任务保持
`UP-TO-DATE` 被跳过）。**不要**为了「干净」去删 `build/intermediates`，
那会把增量缓存全部摧毁，代价是十几分钟的重建。
